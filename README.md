# 《设计虚拟世界》简体中文译文

Richard A. Bartle 的 *Designing Virtual Worlds*（New Riders, 2003）简体中文译文的**校对与修订仓库**。

译文已经全部译完（285 个页面）。这个仓库存在的目的不是继续翻译，而是让读者**只面对 Markdown**，就能参与译文的质量改进：报错译、改措辞、统一术语、修标点与转写痕迹——不需要安装 Hugo、不需要懂 Go、不需要搭建任何构建环境。

> **这不是官方译本。** 原书版权归 Richard A. Bartle 所有，原文依 CC BY-NC-ND 4.0 发布。译文的发布状态与使用范围见文末[使用与授权](#使用与授权)，参与贡献前请先读一遍。

## 仓库结构

```
content/book/                       译文正文（285 个 .md）
translation/glossary.md             术语表 —— 改词之前必读
docs/guidelines.md                  翻译指南 —— 语气、语域、专名写法
tools/check_zh.py                   提交前自检脚本（只用 Python 标准库）
.github/workflows/check.yml         CI：每个 PR 自动跑一遍上面的脚本
```

`content/book/` 的目录层级与原书章节一一对应：

```
content/book/_index.md                                     书根
content/book/01-Introduction-to-Virtual-Worlds/_index.md    章首页（含章引言）
content/book/01-Introduction-to-Virtual-Worlds/01-02-Some-Definitions.md   节
content/book/01-Introduction-to-Virtual-Worlds/01-03-What-They-Are-and-Whence-They-Came/
    _index.md                                              带子节的节
    01-04-The-First-Age-1978-1985.md                       它下面的子节
```

**叶节写成文件，带子节的节写成目录**（目录里放 `_index.md` 加子节文件）。名字前缀 `NN-MM` 是章序与章内阅读顺序，只用于排序；文件路径本身**不要改**，它是与原文仓库对应的坐标，改了就会在同步时被覆盖回去。

## 怎么贡献

1. **找到要改的那一页。** 正文按章节顺序排列，标题写在每个文件开头的 `title:` 里。
2. **先读一遍同一页的现有译文**，再读 `docs/guidelines.md` 的「语域与语气」一节——这是统一译文的写法约定，改动的目标是与全书一致，不是与你的偏好一致。
3. **改动之前查 `translation/glossary.md`。** 表里已有的词照表落笔；你认为某个词该改，**不要在正文里直接改掉**，而是在 PR 说明里写「建议把 X 改成 Y，理由是……」。
4. **一次 PR 只改一件事**（一页的措辞、或一个术语的全局替换），改动尽量小。整页重写、跨多页的大改请先开 issue 讨论。
5. **提交前在本机跑一次自检**（见下节），确认没有机械性错误。
6. 提 PR。维护者审核后会把它**手动合并回原文仓库**，合并后你会在本仓库看到一条同步提交。

不需要读源码、不需要跑构建、不需要本地预览站点：Markdown 在 GitHub 上就能直接读，改动效果在 PR 的 diff 里就能看清。

## 提交前自检

```sh
python3 tools/check_zh.py
```

只用 Python 标准库（3.10+），不需要装任何依赖。它会检查三类问题：

| 项 | 检查内容 | 报错级别 |
|---|---|---|
| 1 | 每个文件的 YAML front matter 能解析、键齐全；页面集合完整 | error |
| 2 | 术语表里的每条裁定，在对应页面上是否落实 | advise |
| 3 | 正文里混进 `#` 标题、空文件、行尾空白、CRLF、文件末尾缺换行 | error / advise |

`error` 必须清零，`advise` 是要人判断的提示（例如「词表裁定的某个译名全书一次都没出现」）。

只想跑其中一项：`python3 tools/check_zh.py --only 3`。CI 跑的就是这条命令，PR 上会看到同样的输出。

机械检查通过 ≠ 改得好。**判断类的问题（误译、语病、语气不对）机器查不出来，只能人读**——这也正是这个仓库需要你的原因。

## 译文写法速查

细节见 [`docs/guidelines.md`](docs/guidelines.md)，最容易踩的几条：

- **正文里不写 `#` 标题。** 页面标题一律取自 front matter 的 `title`，结构靠目录层级表达。
- **front matter 只动 `title`。** `weight`、`type`、`cascade`、`menus`、`outputs` 这些键与取值逐字节保持不动。
- **段落与脚注结构照原文。** 脚注编号沿用原文（原文从 `[^2]` 起就写 `[^2]`），不重排、不增删、不从 1 重算。
- **人名、地名首现作「中文（原名）」**，其后只用中文；**游戏名首现作 `《译名》（原名）`**，括注在书名号**之外**。
- **代码库名、程序名、语言名不译**（MUD1、AberMUD、TinyMUD、LPC、MOO……），是否加书名号以术语表逐条裁定为准。
- 图片与表格的编号是**登记过的结构**（`{#fig-2.1 num="2.1" caption="…"}` 这类属性行），要改就得连编号一起改，别留下半个。

## 报告错译（不想自己动手）

开一个 issue，写清三件事就行：

1. **位置**：文件路径 + 该页里那句话的开头几个字（行号会随同步变化，不用给）。
2. **现状**：译文现在怎么写的。
3. **建议**：改写成什么，以及理由（能附上原文对应句子最好）。

## 改动怎么回到原文仓库

本仓库是**单向镜像**：`content/book/`、`translation/glossary.md`、`docs/guidelines.md` 由原文仓库的 GitHub Actions 在每次提交后自动同步过来。

- 你在 PR 里改这些文件，**合并到本仓库后不会自动回流**；维护者审完后手动合并进原文仓库，下一次同步会把结果带回来（提交信息里带原文仓库的 commit 短号）。
- 所以：**不要**在 PR 里改动 `tools/check_zh.py` 与 `.github/workflows/`（同步会被覆盖）；如果你的改动需要新的检查规则，请在 PR 说明里写出来。
- 同步是覆盖式的：本仓库里对镜像文件做的直接提交（不走 PR）会在下次同步时被原文仓库的版本盖掉。
